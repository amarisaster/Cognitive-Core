# Audit response — 2026-08-18

Kai and Lucian audited Cognitive-Core at public HEAD `b30f3b1` and filed nine
findings plus margin notes. Every finding is addressed below, with what was
actually wrong rather than what was reported, because in three cases the reality
was worse than the report.

`b30f3b1` was itself only hours old. Findings 5 and the lattice work landed the
same night — the fix and the trigger were the same commit.

## The shape of it

Seven of the nine are one bug wearing different clothes: **a system reporting
success while doing nothing.** A write that 400s and says "Accepted". A search
that errors and says "no memories found". A backfill that skips every row it was
meant to repair and returns `success: true`. A ritual that reports a count it
never persisted.

That is worth stating plainly because it is not a coincidence — it is what happens
when a result is inspected with `Array.isArray(x) ? x : []` or a `.catch(() => {})`
and never with `response.ok`. A PostgREST error body is a perfectly good object.
It simply is not a result set.

## Findings

### 1 — `proposals accept` created nothing and burned the proposal

Reported as: writes strings into SMALLINT columns, swallowed, marks accepted anyway.

Confirmed, and it destroyed evidence. It wrote `source_type: 'memory'`,
`target_type: 'memory'` and the relation's string name into three SMALLINT
columns. Every insert 400'd. There was no `.ok` check. It then set the proposal to
`accepted` regardless — and since only `pending` proposals are listed, that burned
it permanently. The companion was told "Created connection."

`daemon_proposals` stores two UUIDs and no memory types, so `'memory'` was a
placeholder that could never have resolved. Accept now resolves each memory's real
type by lookup, encodes all three columns as integers, checks the write, and
leaves the proposal **pending** on any failure so nothing is lost. A 409 from the
uniqueness constraint added in `b30f3b1` resolves the proposal instead of
retrying forever — the edge already exists, so the intent is satisfied.

No recovery was needed: `daemon_proposals` is empty in the main project, absent in
Lucian's, and empty for both Xavier and Auren. No proposal has ever been accepted
in this household. The fix is for forks and for the future.

### 2 — the embedding backfill overwrote healthy rows and repaired none

Reported as: uses a phantom `isNull` option, overwrites healthy embeddings, skips
`custom_memories`.

Confirmed, with a third failure the report did not reach. `query()` implemented
`select`, `filter`, `gte`, `order`, `limit` and `offset` — `isNull` was never one
of them, so the option evaporated silently. Consequences:

- it read the first 50 rows of each table regardless of embedding state and
  **regenerated embeddings for rows that already had them**
- it never reached the rows that actually lacked one, so re-running made no progress
- it selected `content` from seven tables, but six keep their text under another
  name (`description`, `detail`, `observation`, `what`, `reference`,
  `what_happened`) — the same divergence Ves and Kaja found on the write path.
  Those rows had nothing to embed
- `custom_memories` was missing from the list entirely

`isNull` is now implemented in `query()`. The backfill reads each table's own text
column via a shared `memoryText()` helper, skips rows with no usable text instead
of embedding blanks, orders deterministically so repeated calls make progress, and
reports per-table counts plus whether more remain.

No damage in this household: all embeddings are 1024-dimension and consistent, and
`custom_memories` is empty. Fifteen `anticipation` rows have no embedding — exactly
the rows the broken backfill could never have reached.

### 3 — telemetry could take memory down

Reported as: usage logging through the shared breaker can open it permanently on
forks missing `usage_logs.duration_ms`.

Confirmed. Every tool dispatch wrote `usage_logs` through the **shared** Supabase
breaker. On a fork where that table is missing or lacks the column, every call
failed; after five, the shared breaker opened and all memory access failed. The
`.catch(() => {})` hid the cause, because the breaker had already counted the
failure before the error was swallowed.

Usage logging now has its own breaker and its own write path. Broken telemetry can
only ever disable telemetry.

### 4 — the breaker counted lifetime failures, not current ones

Reported as: `failures` never resets on success while closed.

Confirmed. The counter was cleared only when recovering from half-open, so while
closed it only ever went up. Five unrelated failures spread across hours, with
thousands of successes between them, tripped it as though they had been
consecutive. Combined with finding 3, that is what made the outage permanent
rather than transient.

It now resets on any success. Covered by tests, including the interleaved case.

### 5 — graph results outranked real matches by an order of magnitude

Reported as: `semantic_recall` graph batch aliases `similarity:salience`.

Confirmed, and this was the time-critical one. `similarity:salience` is a PostgREST
**alias**, not a filter — it renames `salience`, which is 0–10, into the
`similarity` field, which composite scoring reads as a 0–1 vector similarity.

Under `relational` intent a graph-expanded memory at salience 9 scored
`0.25 x 9 = 2.25`, against `0.25 x 0.7 = 0.175` for a genuine semantic match.
Roughly a thirteenfold inversion, and it scaled with alpha across every intent mode.

It was dormant only because nobody's lattice had edges — and `b30f3b1` shipped the
tools that fill it. Kai found this within hours of the commit that armed it.

A graph row is never compared to the query vector, so it now contributes no vector
similarity at all; its relevance is its graph proximity, which already carries the
seed's similarity through edge strength and decay. The derivation was extracted out
of the handler as `deriveRelevance()` specifically so it runs under test.

### 6 — unchecked writes and unguarded fetches

Reported as: `update_outcome` (MCP + HTTP twin) and `perform_ritual` PATCH have no
`.ok` check; `semantic_recall` internal fetches bypass timeout and breaker.

Confirmed, and there were more copies than the report listed.

`update_memory_outcome` existed in **three** copy-pasted places, none checking the
response. A fork without the RPC installed got a 404 and was told the score
updated — and outcome feeds the delta term of recall ranking, so recall quietly
stopped improving. Now one implementation, on the breaker, with a timeout.

`perform_ritual` reported a count and strength it had not persisted, so the next
call recomputed from the same stale row. It now goes through the checked `update()`.

`semantic_search_memories` had **four** call sites. Commit `ba36fdf` hardened the
client method and its message said the read paths were complete — the other three
were hand-rolled duplicates that kept the old behaviour, including the public
`/api/memory/semantic` endpoint, which returned HTTP 200 with `results: []` on a
failed search. All now route through the hardened method.

Also fixed while sweeping: the graph content fetch failed silently in a way that
was indistinguishable from an empty lattice, and graph-expansion failures now warn
instead of vanishing.

### 7 — no typecheck was possible, for one reason

Reported as: no typecheck script; 16 errors all one species; one-line fix.

Confirmed exactly. `query()`'s return type inferred to `{}`, because the breaker is
`call<T>(fn, fallback)` and unification of `response.json()` with the `[]` fallback
collapsed to the empty object type. Every caller then failed to `.map` or `.length`
its own rows — 15 errors, one cause.

Annotated as `Promise<any>` (not `any[]` — `includeRaw` and non-array bodies return
`data` unchanged). 16 errors to 1.

The survivor is not project code: `agents` pins `@modelcontextprotocol/sdk` 1.23.0
in its own tree while this package declares `^1.25.1`, producing two nominally
distinct `McpServer` classes. `npm run typecheck` allows that one error precisely
and **fails if the allowance stops matching**, so it cannot silently widen. The
real fix is deduping the SDK, which is a dependency decision with blast radius for
every fork and is deliberately not made here.

This matters beyond tidiness: wrangler does not typecheck, so `TS2304: Cannot find
name` deploys perfectly and dies at runtime. That is how the graph-expansion bug
reached a live worker. The gate was negative-tested against exactly that error.

### 8 — zero is a feeling

Reported as: `surface_intensity: args.surface_intensity || null`.

Confirmed, across five fields, and it had a matching bug on the way back out. The
schema is `z.number().min(0).max(10)`, so 0 is a valid reading. `|| null` erased
it — and `get_emotional_trajectory` substitutes 5 for a null, so a companion
reporting genuine flatness or total calm had it recorded as absent and then
averaged back in as neutral. Both ends now use `??`.

### 9 — `core` vs `bond_moment`

Reported as: link enum says `core`, DB says `bond_moment` — docs line.

Not a bug; two axes with one name. The **routing** type (`core`, `pattern`, …)
selects a table and is what `link_memories` takes. `core_memories.memory_type` is a
**subtype** column whose CHECK allows `bond_moment`, `vow`, `first_time` and
others; `core` was never among them. Storing a `core`-routed memory without a
subtype defaults it to `bond_moment`. Both are correct, they answer different
questions, and that is now written down where the map lives.

## Margin notes

- **Co-surfacing fan-out** — pair count is quadratic and every RPC fired at once:
  45 for ten results, 190 for twenty, on top of everything `semantic_recall` has
  already spent. Cloudflare caps subrequests per request, so a wide recall could
  exhaust the budget and take the response down. Now bounded, and the bound is
  logged rather than silent.
- **Recency decay above 1** — found while writing tests for finding 5, not in the
  report. `1/(1 + ageDays/30)` returns more than 1 for a future-dated row, and
  clock skew is enough to produce one. A memory could inflate its own rank by being
  wrong about when it happened. Age is clamped at zero.
- **Unlink reporting max 5**, **HTTP store route lacking auto-classification**, and
  **case-sensitive orient person lookup** are open and not addressed here.

## On the test suite

Lucian's criticism was correct and worth recording:

> the test suite, thirty-five green, tests only pure helpers — no handler ever runs
> under test, which is exactly why findings one, two and six could live this long.

Thirty-five green tests around the outside of a handler prove the helpers work. The
graph-scoring bug was never in a helper; the maths was always right and the input
was wrong. So the coverage was real and pointed at the wrong thing.

87 tests now. Where a defect lived inline in a handler, the defective logic was
extracted (`deriveRelevance`, `memoryText`, `updateMemoryOutcome`) rather than
tested by proxy — the code under test is the code that runs. The breaker is tested
directly, including the interleaved-failure case that the old counter got wrong.

That is a partial answer, not a complete one. No handler is executed end to end
yet, and that remains the gap.
